# 文章编写规范

Zwiki 是**技术场景速查库**，不是百科全书，也不是官方手册的复制版。文章目标是：遇到一个常见问题时，读者能快速找到最短可执行方案。

## 1. 内容定位

每篇文章只解决一个主要场景，优先写：

```
结论
↓
最短操作步骤
↓
验证方法
↓
常见异常分支
↓
必要风险提醒
↓
官方资料链接
```

不要大篇幅复制官方背景、参数说明、概念定义和完整功能清单。需要深入学习时直接给官方文档链接。

## 2. 标题要短

标题只保留“对象 + 操作/问题”。不要把平台列表、背景、结论全部塞进标题。

推荐：

```
Linux 批量运维速查
Linux 离线软件安装速查
K3s 日常运维速查
Nginx 故障排查速查
```

避免：

```
Windows / Linux / macOS 批量运维 Linux 主机完整使用说明
```

文件名使用稳定的小写英文和连字符，例如：

```
linux-batch-operations.md
linux-offline-package-management.md
```

已有文章默认不改路径；只需要让展示标题更简洁时，修改 H1 和 `SUMMARY.md` 即可。

## 3. 优先给最简单可用方案

如果有多种实现方式：

1. 先给最常用、最容易落地的方法；
2. 再说明更安全或更正式的生产方案；
3. 其他方案只做简短对比，不展开成多套完整教程。

例如 Ansible 密码登录，可以先给：

```ini
ansible_user=root
ansible_password=CHANGE_ME
```

然后明确说明：这是临时、测试环境的最简方法；长期使用改为 SSH Key 或 Ansible Vault。

## 4. 命令必须能直接用

* 命令块前说明在哪台机器执行；
* 一条命令尽量完成一件事；
* 给出最关键的验证命令；
* 高风险操作先小范围测试；
* 不为了展示“专业”堆大量低频参数。

涉及批量变更时，优先提供：

```
先 1 台验证 → 再小批量 → 最后全量
```

## 5. 背景知识控制篇幅

只保留理解操作所必需的原理。

以下内容通常只给官方链接：

* 完整参数表；
* 完整 API 参考；
* 组件架构原理；
* 全量兼容矩阵；
* 官方安装手册已经覆盖的长流程。

如果官方资料经常更新，不在 Zwiki 重复维护一份易过期的副本。

## 6. 文档信息保持精简

确实需要时保留少量信息：

* **适用范围**
* **适用版本**
* **最后验证**
* **来源**

不要为了元数据创建大表格。

## 7. 表格只用于比较

适合表格：

* 方案对比；
* 版本兼容；
* 参数清单；
* 故障现象与处理对应关系。

普通说明和少量键值信息使用段落或列表。

## 8. 安全边界

不得提交真实：

* 密码；
* Token；
* Cookie；
* 私钥；
* 客户信息；
* 未脱敏日志和内网敏感数据。

文章为了说明配置密码时统一使用 `CHANGE_ME`、`example.com`、`192.168.1.x` 等示例值。

## 9. 来源和链接

优先引用官方文档、官方仓库和一手资料。

内部文章使用相对链接；深入内容直接链接官方资料，不在 Zwiki 重新抄一遍。

## 10. 修改入口

Zwiki 的 GitBook 站点应启用原生 **Edit on GitHub/GitLab** Page Action，让每个页面直接跳转到对应 GitHub 源文件。

具体设置见 [Zwiki 快速修改](quick-edit-and-feedback.md)。
