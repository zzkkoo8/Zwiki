# 提示词

提示词的目标不是“写得长”，而是把任务目标、上下文、约束和验收标准表达清楚，让模型减少猜测。

## 推荐结构

```text
目标
→ 要解决什么问题

上下文
→ 当前项目、环境、已有文件、已确认决策

约束
→ 不能做什么、技术栈、风险边界

执行要求
→ 需要检查、修改、测试哪些内容

验收标准
→ 什么结果算完成

输出格式
→ 只要结论、表格、MD、代码或执行结果
```

## 通用模板

```text
目标：
[一句话说明最终目标]

上下文：
[现状、环境、已有方案]

约束：
- [不能修改的内容]
- [必须使用的技术/版本]
- [安全或兼容性要求]

执行：
1. 先检查现状和相关文件。
2. 给出最小可行方案。
3. 实施后运行验证。
4. 发现异常先定位根因，不要盲目叠加修改。

验收：
- [可观测结果 1]
- [可观测结果 2]

输出：
[希望得到的格式]
```

## Coding Agent 提示词

对于 Codex、Claude Code、Cursor 等 Coding Agent，优先补充：

- 仓库路径和目标分支；
- 必须读取的 `README.md`、`AGENTS.md`、设计稿；
- 允许修改的范围；
- 必须运行的测试/验收命令；
- 是否允许新增依赖；
- 完成前必须检查 `git diff`。

示例：

```text
先读取 AGENTS.md 和现有实现，定位问题根因。
只修改解决当前故障必需的文件，不做无关重构。
修改后运行现有测试，并检查 git diff 是否超出任务范围。
如果测试失败，先定位失败原因再继续修改。
```

## 文档整理提示词

```text
先搜索是否已有同主题文章，优先修改存量内容。
保持原路径和无关章节不变。
新增命令必须写明预期结果、异常判定和风险。
涉及版本或官方行为时优先核对官方资料。
```

## 常见问题

### 提示词越长越好吗？

不是。重复规则、无关背景和过多角色设定会增加上下文成本。优先保留会改变执行结果的信息。

### 是否应该把所有规则都写进每次提示词？

不需要。长期规则应放在仓库级 `AGENTS.md`、项目规范或 Skill 中；单次提示词只描述当前任务和必要例外。

### Prompt、Skill、AGENTS.md 如何分工？

```text
Prompt
→ 当前一次任务

AGENTS.md
→ 当前仓库长期规则

Skill
→ 可跨项目复用的方法和流程
```
