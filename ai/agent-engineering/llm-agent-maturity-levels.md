# LLM Agent 能力成熟度：从会用模型到构建自进化系统

## 结论

评估一个人或团队的 Agent 工程能力，不应只看用了多强的模型、接了多少工具或并发开了多少 Agent，而应看：**能把多大范围的任务交给系统，系统能否在权限边界内完成，并通过可重复的验证证明结果正确。**

本文把能力划分为十级，作为工程讨论和自测框架，而非官方标准：

- **L1–L3：使用 AI**——从问答、Coding Agent，走向工具、知识和上下文集成。
- **L4–L6：设计系统**——上线、观测、评估，并把失败转化为测试和规则。
- **L7–L8：组织规模化协作**——协调多 Agent，依赖可验证产出控制规模。
- **L9–L10：构建进化机制**——优化 Agent 外部执行结构，并把运行数据转化为下一轮改进素材。

级别不等于模型智商排名。它衡量的是工程责任、自治程度、可验证性和治理能力。

## 十级能力模型

### L1：把 LLM 当搜索引擎

用网页或客户端提问、查知识、总结内容。主要产出仍是回答文本。

**自测：** 日常使用记录中，有多少结果能直接用于工作，而不只是读完就结束的对话？

**升级方向：** 提供必要的任务背景、文件和目标格式，让模型产出可执行的内容。

### L2：使用 API 和 Coding Agent

把模型接入 Codex、Claude Code、OpenCode 等工具，让它读取项目、编辑文件、运行命令和测试。

关键不只是配置 API Token，还包括识别不同模型在规划、长任务、自主执行和收尾习惯上的差异，并审查 diff、测试结果和权限边界。

**自测：** 不打开网页聊天窗口，能否让 Agent 修改项目、运行测试，并交付可审查的变更？

### L3：集成 MCP、Skill、API 与 RAG

为 Agent 提供原本不可见的工具和知识：内部 API、业务系统、文档检索、可复用 Skill 等。

这一级的核心挑战是**上下文工程**：信息是否相关、是否完整、是否放在正确位置。工具和 Skill 的数量不代表质量；不相关的检索结果、冗长上下文和错误工具描述反而可能降低效果。

**自测：** 能否解释 MCP、Skill 和 RAG 分别解决什么问题，并指出配置不当时会出现什么失败模式？

### L4：交付并运行一个真实系统

把 Agent 做成别人也会使用的系统，并承担部署、权限、成本、可用性和故障恢复责任。

运行环境中的任务往往没有完整测试集。尤其是运维场景，Agent 可能面对磁盘耗尽、网络中断或服务异常等不确定状态。应先收集证据、提出诊断和建议，再依据风险等级决定是否允许执行。

**自测：** 是否有真实用户、可追踪成本、明确权限和故障降级方案？

### L5：Harness、Trace 与系统化调试

Harness 是模型外部组织和约束执行的工程层，通常包含任务规划、上下文管理、工具、权限、状态、恢复、验证和观测。

出现失败时，不应只反复要求模型“更努力”，而应读取 Trace，定位具体哪一步偏离目标，再调整工具描述、上下文、流程或门禁，并通过同一评测集比较前后结果。

**自测：** 能否指出一条具体 Trace 中的失败步骤、修改的 Harness 层，以及修改前后的指标变化？

### L6：让系统从错误中迭代

将重复出现的失败转化为持久改进：回归测试、约束规则、工具校验、工作流修正或更好的交接文档。

长任务还需要明确的上下文交接。与其不断压缩一段越来越长的历史，不如生成结构化进度、决策、未完成事项和验证结果，再由新上下文继续执行。生成者与评估者应尽量分离，避免 Agent 只凭自评宣布成功。

通知器和会话管理同样重要：长任务必须能报告完成、失败、等待输入和需要人工介入的状态。

**自测：** 昨天犯过的错误，今天是否仍会重复？如果不会，是哪条测试或门禁阻止了它？

### L7：管理几十到上百个 Agent

当单个 Agent 或少量 Agent 不足以满足任务规模时，才考虑集群协作。

共享文件、锁和乐观并发控制都可能带来冲突、空转、重复劳动或风险规避。常见的组织方式是规划者分解任务、工作者独立执行、评审者检查结果，并约定文件所有权、接口和合并规则。

增加 Agent 数量不保证吞吐量增长。过多协调角色也可能成为新的瓶颈。

**自测：** 能否说明每个 Agent 的职责、依赖关系、冲突处理方式、验证状态和成本？

### L8：规模化运行成千上万个 Agent

这一层的主要难题不再是“如何启动更多 Agent”，而是如何让规模扩大后，产出仍然正确、可追踪、可合并。

可行的基础设施通常包括隔离的工作区、任务认领与状态协议、共享上下文、提交与合并规则，以及独立验证器。对数学证明等领域，形式化检查器可验证证明链；还需要检查器确认系统证明的仍是原始目标，而非悄悄弱化后的问题。

**自测：** 当并发规模扩大十倍时，依据什么证据相信质量没有失控？

### L9：让 Agent 的外部执行结构可进化

即使模型参数冻结，Agent 的工具定义、程序性知识、工作流、提示、记忆结构和执行策略仍可迭代。

一个稳健的改进循环应当比较成功与失败轨迹，提出结构变更，在留出评测集上验证，并只接受达到质量门槛的改动。失败或被否决的方案也应记录，避免反复尝试同一条无效路径。

**自测：** 能否明确指出 Agent 的哪个外部组件由运行数据驱动改进，以及最近一次改进通过了什么验证？

### L10：建立数据驱动的自我改进飞轮

把改进拆成三个速度层次：

1. **运行时循环：** 积累任务结果、成功路径、失败原因和可复用经验。
2. **系统优化循环：** 批量评估并改进 Skill、提示、工具描述、程序图或 Harness。
3. **训练数据循环：** 将经过筛选、脱敏和质量检查的轨迹转为 SFT / RL 等训练素材，供后续模型训练使用。

最重要的控制条件是：**评测器和安全门禁不能被自改流程绕过或放宽。** 否则系统可能通过降低验收标准制造“进步”的假象。评测器应独立于被优化对象，并保留基线、留出集、版本记录和回滚能力。

**自测：** 今天的运行数据能否在不降低验收标准的前提下，成为明天能力提升的依据？

## 三个工程结论

### 1. 级别之间的差异，本质上是责任边界的差异

低级别由使用者逐次判断结果；系统化阶段需要权限、审计和验证；规模化阶段则需要制度化的任务分配和评测治理。自治程度越高，越不能依赖人工盯住每一步。

### 2. 模型能力不是全部，Harness 是可积累的工程资产

模型负责推理和生成，Harness 决定任务如何分解、上下文如何提供、工具如何调用、失败如何恢复、结果如何验证。更换模型可能提升能力，但缺少执行环境和验证机制，仍然难以稳定交付。

### 3. 规模化的前提是产出可被可靠判别

优先选择有确定性验证器的任务，例如编译、类型检查、单元测试、Schema 校验和可执行检查脚本。LLM-as-judge 可用于辅助评价，但本身具有不确定性；没有明确验收标准的领域，不应仅凭增加 Agent 数量来宣称实现了可靠自治。

## 实施路线

| 当前阶段 | 下一步优先建设 |
| --- | --- |
| L1 | 让模型产出可直接使用的任务结果 |
| L2 | 建立代码修改、测试、Diff 审查的闭环 |
| L3 | 接入必要工具和知识，控制上下文质量 |
| L4 | 补齐最小权限、成本观测、降级和人工接管 |
| L5 | 保存 Trace，定位失败原因并做可重复评测 |
| L6 | 把失败沉淀为回归测试、规则和交接状态 |
| L7 | 明确任务协议、工作区隔离、评审和成本预算 |
| L8 | 建立可扩展的协调机制和独立验证器 |
| L9 | 对外部执行结构做数据驱动的受控优化 |
| L10 | 建立轨迹筛选、训练数据治理和不可绕过的评测门禁 |

## 风险与边界

- 十级模型是用于自测和工程讨论的个人归纳，不是官方认证标准。
- 规模、成本、基准分数和研究结论依赖具体任务、模型、评测集及统计口径，不宜直接横向比较。
- 用户提供的原文包含若干 2026 年数据及论文、厂商案例；本文保留其核心框架，但未逐项独立核验所有数字。引用具体数值前应回到原始论文或官方发布页面确认。
- 运维 Agent 应遵循最小权限、先诊断后执行、高危操作人工审批、可审计和可回滚原则。
- 自我改进不能修改或绕过自身的安全策略、权限边界和验收门槛。
